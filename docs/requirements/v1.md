# V1 Requirements

Status: **Draft — awaiting product-owner approval**
Source: [`product-brief.md`](product-brief.md) (original brief, kept unchanged for traceability).

This document turns the brief into numbered, testable requirements and records
the adjustments made after reviewing the brief. Where this document and the brief
differ, this document wins once approved.

## 1. Adjustments to the brief

| # | Brief said | Adjustment | Why |
|---|------------|------------|-----|
| A1 | "The backend must never be able to decrypt the vault" (§5.1, §5.3) | Add an explicit **code-delivery threat**: whoever controls the web app's hosting can ship code that captures the master password. Mitigations are required (R-SEC-10…13) and the residual risk is documented. | Zero-knowledge storage does not protect a web client the server itself delivers. |
| A2 | "Do not expose unnecessary secret material to JavaScript" (§5.2) | Keep the narrow WASM interface, but document that WASM memory is readable by same-origin JS. It is a hygiene boundary, not an isolation boundary. | Avoid overstating a security property. |
| A3 | Account authentication is "separate" but unspecified | Specify it: an **auth key pair derived from the master password and the Account Secret Key**, plus a **separate recovery auth key** derived from the Recovery Key, plus **per-device keys**. See R-AUTH-*. | Recovery must also restore *server* access, not just the VMK. |
| A4 | "A second device can securely enroll" — method unspecified | V1 enrollment = email + Account Secret Key + master password, followed by an in-app notice on every other device. Approval from an existing device (QR) is V1.1. | Simplest flow that needs no second device to be at hand. |
| A5 | Device revocation "prevents future synchronization" | Also add **VMK rotation** (re-encrypt every item) to V1, and state that revocation alone does not take back data or keys a device already holds. | Revocation without rotation does not protect against a compromised device. |
| A6 | Argon2id "calibration strategy for supported devices" | **Fixed parameters per envelope**, chosen at account creation for the weakest supported device; changed only by re-wrapping. | One envelope is shared by all devices; per-device calibration would weaken all of them. |
| A7 | "Recovery Keys must be replaceable" | Using the Recovery Key **forces** a new master password, and a new Recovery Key before the flow completes. | A used Recovery Key should be treated as exposed. |
| A8 | UX section lists identities and payment cards | V1 item types are **Login, Secure Note, SSH Key** (TOTP is a field on Login). The data model stays open to more types. | Match V1 functional scope (§7). |
| A9 | "macOS companion where native integration is required" | V1 macOS = **Rust CLI + SSH agent daemon (launchd)**. A native app (Touch ID, per-use confirmation UI) is V1.1. | Smallest native surface that satisfies the SSH requirements. |
| A10 | SSH keys — types unspecified | V1 supports **Ed25519 and ECDSA (P-256)**. RSA import is accepted but signing with RSA is behind an explicit decision (RUSTSEC-2023-0071 timing issue in the `rsa` crate). | Known side-channel in the main Rust RSA implementation. |
| A11 | New-device notifications by unspecified channel | In-app notice on all other devices; email optional and off by default. | Email adds a provider and more server-visible personal data. |
| A12 | "Copy… with clear user feedback" | Native clients clear the clipboard after a timeout. The PWA cannot reliably clear it; the UI says so. | Browser platform limitation. |
| A13 | Doc list (§10) lacks sync, devices, roadmap | Add `docs/architecture/sync.md`, `docs/security/devices.md`, `docs/roadmap.md`. | §12 asks for these deliverables. |
| A14 | "Independent review" before production credentials | Name the review gate: external review of `cryptographic-design.md`, plus fuzzing and published test vectors, before storing real credentials. | A definition of done needs a checkable gate. |

## 2. Requirements

Priority: **M** = must for V1, **S** = should for V1, **L** = later.
Every **M** requirement needs at least one automated test or a documented manual check.

### 2.1 Account and unlock

| ID | Pri | Requirement | Acceptance criteria |
|----|-----|-------------|---------------------|
| R-ACC-1 | M | Create an account locally: generate Account Secret Key, VMK and Recovery Key on the device; choose a master password. | No plaintext key, password or Secret Key is sent to the server (verified by request-capture test). |
| R-ACC-2 | M | Show an Emergency Kit (Secret Key + Recovery Key + instructions) and require the user to confirm they saved it. | Account creation cannot finish without confirmation. Kit is printable/downloadable locally; never uploaded. |
| R-ACC-3 | M | Unlock with master password; Secret Key is read from local device storage. | Wrong password → generic error, no detail on which input was wrong. |
| R-ACC-4 | M | Offline unlock from the local encrypted cache. | Unlock and read items with network disabled. |
| R-ACC-5 | M | Automatic lock after a configurable idle time (default 10 min) and on explicit lock. | After lock, the VMK and item keys are zeroized; reading an item requires unlock. |
| R-ACC-6 | M | Master password change re-wraps the VMK only. | Item ciphertexts are byte-identical before and after (test). |
| R-ACC-7 | M | Account Secret Key rotation re-wraps the VMK and re-derives the auth key. | Old Secret Key no longer unlocks or logs in. |

### 2.2 Recovery

| ID | Pri | Requirement | Acceptance criteria |
|----|-----|-------------|---------------------|
| R-REC-1 | M | Recover on a new device with email + Recovery Key, without the master password or Secret Key. | End-to-end test: fresh device recovers and reads all items. |
| R-REC-2 | M | Recovery forces a new master password, new Secret Key and new Recovery Key. | After recovery, the old Recovery Key fails (test). |
| R-REC-3 | M | Recovery Key rotation replaces the recovery envelope and recovery auth key atomically. | Old Recovery Key fails; new one works; no window where neither works. |
| R-REC-4 | M | Clear guidance on what each secret does and what happens if it is lost. | UX review checklist. |

### 2.3 Authentication and devices

| ID | Pri | Requirement | Acceptance criteria |
|----|-----|-------------|---------------------|
| R-AUTH-1 | M | Login by signing a server challenge with an auth key derived from (master password, Secret Key). The server stores only the public key. | Server DB dump contains no value that allows offline password guessing without the Secret Key. |
| R-AUTH-2 | M | Recovery login by signing a challenge with a key derived from the Recovery Key. | Separate public key stored; replaced on rotation. |
| R-AUTH-3 | M | Each device has its own key pair; sessions are short-lived tokens bound to a device. | Token from device A is rejected when presented with device B's id. |
| R-DEV-1 | M | Device registration, listing (name, platform, first/last seen) and revocation. | Revoked device: all API calls → 401 within one request. |
| R-DEV-2 | M | New-device enrollment shows a notice on all other devices at next sync. | Integration test. |
| R-DEV-3 | M | VMK rotation: new VMK, every item re-encrypted, all envelopes re-wrapped. Offered after revocation. | Revoked device's cached VMK cannot decrypt any item written after rotation. |
| R-DEV-4 | L | Enrollment approval from an existing device (QR). | — |

### 2.4 Vault items

| ID | Pri | Requirement | Acceptance criteria |
|----|-----|-------------|---------------------|
| R-ITEM-1 | M | Item types: Login (title, username, password, URLs, notes, optional TOTP), Secure Note, SSH Key. | Create/read/update/delete for each type. |
| R-ITEM-2 | M | Every item is encrypted on the device before it is written to IndexedDB, disk or the network. | Storage inspection test finds no plaintext. |
| R-ITEM-3 | M | Search across titles, usernames and URLs of the unlocked vault (client-side only). | Search works offline; no search terms leave the device. |
| R-ITEM-4 | M | Sensitive fields masked by default; reveal and copy are explicit actions with feedback. | UI tests. |
| R-ITEM-5 | M | TOTP codes (RFC 6238; SHA-1/256/512, 6–8 digits, 30 s default) generated locally. | RFC 6238 test vectors pass. |
| R-ITEM-6 | M | Password generator (random characters and word-list passphrase), using a CSPRNG. | Distribution/length tests; no `Math.random`. |
| R-ITEM-7 | S | Native clients clear the clipboard after 90 s if it still holds the copied value. | — |
| R-ITEM-8 | L | Identities, payment cards, attachments. | — |

### 2.5 Synchronization

| ID | Pri | Requirement | Acceptance criteria |
|----|-----|-------------|---------------------|
| R-SYNC-1 | M | End-to-end encrypted sync of items between enrolled devices. | Server sees only ciphertext and the metadata listed in `overview.md` §6. |
| R-SYNC-2 | M | Offline edits queue locally and sync later. | Edit offline on two devices, reconnect, both converge. |
| R-SYNC-3 | M | Per-item revisions with optimistic concurrency; conflicting edits keep **both** versions for the user to resolve. | No silent data loss in conflict tests. |
| R-SYNC-4 | M | Deletes are tombstones; retained ≥ 90 days. | Delete propagates to a device offline for 30 days. |
| R-SYNC-5 | M | Every mutation carries a client-generated id; replays are no-ops. | Retry test: same mutation sent twice → one revision. |
| R-SYNC-6 | M | Devices behind tombstone retention, or with an old schema, do a full resync or are told to update. | Test with a device offline beyond retention. |

### 2.6 SSH and CLI

| ID | Pri | Requirement | Acceptance criteria |
|----|-----|-------------|---------------------|
| R-SSH-1 | M | Import OpenSSH private keys (Ed25519, ECDSA P-256), including passphrase-protected ones. | Fixture keys (test-only, generated) import correctly. |
| R-SSH-2 | M | SSH agent speaking the standard agent protocol on a Unix socket (macOS). | `ssh -T` against a test sshd succeeds via `SSH_AUTH_SOCK`. |
| R-SSH-3 | M | Keys are served only while the vault is unlocked; lock unloads them. | After lock, `ssh-add -l` lists nothing and signing fails. |
| R-SSH-4 | M | CLI: `unlock`, `lock`, `status`, `sync`, `item list/get`, `ssh list/import`, `agent start/stop`. | CLI integration tests. |
| R-SSH-5 | S | Per-use confirmation for signing. | — (native UI is V1.1) |
| R-SSH-6 | L | RSA signing (pending decision D-7). | — |

### 2.7 Security

| ID | Pri | Requirement | Acceptance criteria |
|----|-----|-------------|---------------------|
| R-SEC-1 | M | No secrets in logs, URLs, notifications, analytics, error messages or crash output. | Log-scrubbing test with known canary secrets. |
| R-SEC-2 | M | All encrypted formats carry a version and algorithm id. | Decoder rejects unknown versions with a non-secret error. |
| R-SEC-3 | M | Only reviewed libraries for cryptography; no custom primitives. | Dependency list reviewed in an ADR. |
| R-SEC-4 | M | Cross-platform test vectors (native Rust ↔ WASM ↔ fixtures). | CI job. |
| R-SEC-5 | M | `cargo deny` (advisories, licenses) and `pnpm audit` in CI. | CI job. |
| R-SEC-10 | M | Strict CSP, no third-party scripts, no analytics in the web app. | CSP header test. |
| R-SEC-11 | M | Reproducible web build with a published hash per release. | Two clean builds → identical hashes. |
| R-SEC-12 | S | Service worker pins the installed bundle and warns before activating a changed one. | — |
| R-SEC-13 | M | Web app and API served from separate hostnames; the API cannot change the app bundle. | Deployment config review. |

### 2.8 UX

| ID | Pri | Requirement | Acceptance criteria |
|----|-----|-------------|---------------------|
| R-UX-1 | M | Desktop-first, responsive to tablet and phone widths. | Layout tests at 1280, 768, 390 px. |
| R-UX-2 | M | Full keyboard navigation and accessible labels. | Automated a11y check (axe) has no serious violations. |
| R-UX-3 | M | Visible states: locked/unlocked, sync (idle/syncing/offline/error/conflict), device notices. | UI tests for each state. |
| R-UX-4 | M | Original design system; no 1Password assets, names or copy. | Design review. |

## 3. Out of scope for V1

Unchanged from the brief §7.5: iOS AutoFill, iOS SSH agent, browser extensions,
sharing, enterprise admin, cloud credential injection, multi-person recovery, RBAC.
Also deferred: native macOS app UI, RSA signing, attachments.

## 4. Definition of done (V1)

The brief's §11 list applies, plus:
- Every **M** requirement above has its acceptance check passing in CI or recorded.
- The A14 review gate is passed before real credentials are stored.
